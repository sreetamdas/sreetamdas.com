# But the model flipped

The App Router made React server-first by default.

<Steps>

- `"use client"` everywhere you wanted state or interaction
- React written backwards from how we'd always written it: client-first, functions as first-class citizens
- Only serializable props could cross the server/client boundary
- Composition footgun: importing a Server Component into a Client Component silently forced the whole subtree client-side — wiping away the RSC benefits
- Caching was suddenly a thing you had to think about
- The dev server _seemed_ super slow — and I hated being locked out of Vite
- Then more surface to learn: partial pre-rendering, `"use cache"`, and I grew wary of platform lock-in

</Steps>

<Notes>

- Don't overstate it — App Router is good. The friction is the inversion: server-by-default reframes everything, and it felt like the whole app had to be built _around_ RSCs.
- The composition gotcha is the sneakiest one — no error, no warning, just silently losing the thing you came for.
- The lock-in line is the honest heart of it: "most of my projects have exactly 0 users, and I was wary of being locked into Vercel." Say it lightly — it gets a laugh and it's true.
- The honest gripe: I wanted the server _available_, not _mandatory_.

</Notes>

# Start's bet: the server, opt-in

You don't build the app around the server. It's just there when you reach for it.

<Steps>

- No relearning React — Start is full-stack functionality on top of TanStack Router
- Add the server gradually, per route — you opt _in_, you don't opt out
- Deploy anywhere — no first-party host bending the framework
- TypeScript, first-class, end to end — and built on Vite

</Steps>

<Notes>

# Client-first, server-available

Write your React the way you always have. Reach for the server per route, only where it helps.

<Steps>

- Server-side rendering
- Progressive loading with streaming
- Server routes — public HTTP endpoints
- Server functions — typed RPCs for your own app
- Middleware — client _and_ server halves
- Deploy anywhere, or self-host

</Steps>

<Notes>

- This is the "What" — everything the server gives you, all opt-in. We'll walk each one, then tie them together in one connected example.
- The server is available whenever, wherever. You never invert the mental model to get it.

</Notes>

# Server functions are typed RPC

<ServerFnBuildUp />

A server boundary you can call from loaders, hooks, and components.

`GET` here — so the RPC is HTTP-cacheable. Server Actions are POST-only.

# The part Next does not have

Server function middleware can run on the client and the server.

<MiddlewareBuildUp />

This is the _per-function_ tier. There's also request middleware for every request.

<Notes>

- THE take-home beat: one middleware with a `.client()` and a `.server()` half spanning the network.
- Two tiers: request middleware (all SSR/routes/functions) AND per-function middleware (client + server halves). Next has one edge `middleware.ts` that can't even touch a DB.

</Notes>

# Loader data is cached

```tsx
createFileRoute("/blog/$slug")({
  loader: ({ params }) => getBlogRenderable({ data: params }),
  staleTime: 1000 * 60 * 60 * 24, // fresh for a day
});
```

In Next, caching became a thing to manage. Here it's just `staleTime`, per route.

<Notes>

- How it differs from Next: Next made caching an explicit surface — the `fetch` cache, `"use cache"`, `revalidateTag`, and the mental overhead of knowing which is in play. In Start it's the router's built-in stale-while-revalidate: set a `staleTime`, done.
- Back-navigation is instant while it revalidates in the background. No React Query required — though the same loader can `ensureQueryData` from the Query client you already use.
- Repo proof: every route sets a staleTime — blog 24h, `/stats` 5m, this deck's demos 30s.

</Notes>

# Build-time server functions

# Type safety, the old way vs. Start

<TypeSafetyBuildUp />

<Steps>

- Next Pages: `FoobarPageQuery extends ParsedUrlQuery`, `params!`, `InferGetStaticPropsType` — just to give `params` a type
- Next App Router: every page redeclares `type PageParams = { params: Promise<...> }` and `await`s it — by hand, per route
- Start: one `validateSearch` schema; `useSearch()` returns `PlausibleDateRange` — no `as`, no `params!`

</Steps>

<Notes>

- The "before" code is real — pulled from this repo's git history. The `params!` non-null assertion had an eslint-disable next to it; that's how much we didn't want to write it.
- The App Router `PageParams` boilerplate is the worst part: a Promise you unwrap by hand, redeclared on every single page. No shared type — each route writes its own.
- If a Next person pushes back: "I can zod my searchParams too" — yes, every route, every time, and the cache still doesn't know your schema exists. Concede the parsing, hold the line on integration.

</Notes>

# Composite components: slots

<CompositeBuildUp />

The server tree keeps its slots open. The client fills them with interactive islands — and the server passes typed data _out_.

<Notes>

- This is the clean inverse of the App Router footgun: there, a client import silently dragged the server subtree client-side. Here the server tree stays server-side and hands typed data out to the client island it wraps.
- Three slot types: `children` (no data), render props (server → client data), component props (reusable client components fed server data).
- Be honest about the edges: slots are opaque on the server (`React.Children.map`/`cloneElement` won't work on `props.children` — use render props), and render-prop args must be serializable (they cross React's Flight protocol).
- Still experimental into early v1; server-component serialization uses React Flight today (primitives, Dates, React elements).

</Notes>
