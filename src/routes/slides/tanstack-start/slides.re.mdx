# But the model flipped

The App Router made React server-first by default.

<Steps>

- `"use client"` everywhere you wanted state or interaction
- React written backwards from how we'd always written it: client-first
- Only serializable props could cross the server/client boundary
- Composition footgun: importing a Server Component into a Client Component silently forced the whole subtree client-side — wiping away the RSC benefits
- Caching was suddenly a thing you had to think about
- The dev server _seemed_ super slow
- And I was growing wary of being locked into one platform

</Steps>

<Notes>

- Don't overstate it — App Router is good. The friction is the inversion: server-by-default reframes everything.
- The composition gotcha is the sneakiest one — no error, no warning, just silently losing the thing you came for.
- The lock-in line is the honest heart of it: "most of our projects have exactly 0 users, and I was wary of being locked into Vercel." Say it lightly — it gets a laugh and it's true.
- The honest gripe: I wanted the server _available_, not _mandatory_.

</Notes>

# Type safety, the old way vs. Start

<TypeSafetyBuildUp />

<Steps>

- Next Pages: `FoobarPageQuery extends ParsedUrlQuery`, `params!`, `InferGetStaticPropsType` — just to give `params` a type
- Next App Router: every page redeclares `type PageParams = { params: Promise<...> }` and `await`s it — by hand, per route
- Start: one `validateSearch` schema; `useSearch()` returns `PlausibleDateRange` — no `as`, no `params!`

</Steps>

<Notes>

- The "before" code is real — pulled from this repo's git history. The `params!` non-null assertion had an eslint-disable next to it; that's how much we didn't want to write it.
- The App Router `PageParams` boilerplate is the worst part: it's a Promise you unwrap by hand, redeclared on every single page. There's no shared type — each route writes its own.
- This sets up the whole "types" thread: URL state, server functions, middleware. The payoff is you never write `as` or `params!` again.
- If a Next person pushes back: "I can zod my searchParams too" — yes, every route, every time, and the cache still doesn't know your schema exists. Concede the parsing, hold the line on integration.

</Notes>

# The part Next does not have

Server function middleware can run on the client and the server.

<MiddlewareBuildUp />

This is the _per-function_ tier. There's also request middleware for every request.

<Notes>

- THE take-home beat: one middleware with a `.client()` and a `.server()` half spanning the network.
- Two tiers: request middleware (all SSR/routes/functions) AND per-function middleware (client + server halves). Next has one edge `middleware.ts` that can't even touch a DB.

</Notes>

# 3. Loader data is cached

```tsx
createFileRoute("/blog/$slug")({
  loader: ({ params }) => getBlogRenderable({ data: params }),
  staleTime: 1000 * 60 * 60 * 24, // fresh for a day
});
```

Stale-while-revalidate, per route. Back-navigation is instant; no React Query required.

<Notes>

- The differentiator the docs lead with: built-in SWR caching via TanStack Router.
- `staleTime` / `gcTime` per route, structural sharing, background revalidation.
- Callback to slide 6: the TanStack Query you already use plugs into the loader too.
- Repo proof: every route sets a staleTime — blog 24h, `/stats` 5m, showcase 30s.

</Notes>

# How to start

<Steps>

- `npx tsr init` — scaffold a route tree
- `pnpm dev` — Vite is up almost immediately
- Add a server function, a `validateSearch`, a loader — incrementally, not all at once
- The mental model never inverts: you opt _into_ the server, you don't opt out of it

</Steps>

<Notes>

- The "How" beat — one slide, ~40s. Show that the on-ramp is shallow and additive.
- If someone asks "migrate from Next?": do it route by route. The router doesn't demand a rewrite; you bring a page over, add a `validateSearch`, pick an `ssr` mode. That's the portability pillar paying off.

</Notes>

# Where Next still wins

Be honest or nobody trusts the comparison.

<Steps>

- RSC ecosystem maturity (it's experimental in Start)
- `<Form>` and Server Action form ergonomics
- Built-in image and font optimization
- ISR/PPR that's automatic on Vercel — not just cache headers
- Ecosystem size and hiring familiarity
- And: Start is still a Release Candidate

</Steps>

<Notes>

- Credibility anchor — say it plainly, don't hedge. "I ship Next; I'd still pick it for X tomorrow."
- ISR nuance: Start _can_ do ISR via `Cache-Control`; Next's is automatic and Vercel-tuned. Don't over-concede it.
- Don't rush the list; this is what makes the rest trustworthy.

</Notes>
