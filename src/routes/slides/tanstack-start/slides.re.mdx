# Start's pitch in one sentence

Router-first React, with the server added where it helps.

<Steps>

- Type the URL
- Type the loader
- Type the server boundary
- Choose rendering per route
- Deploy to the runtime you actually want

# 1. URL state is not a string bag

```tsx
export const Route = createFileRoute("/(main)/stats")({
  validateSearch: (search): StatsSearch => ({
    period: parseDateRange(search.period),
  }),
  loaderDeps: ({ search }) => ({ period: search.period }),
});
```

The URL is a state manager with a schema.

<Notes>

- Contrast: search params as a "string bag" everyone re-parses vs. a schema the route owns.
- `validateSearch` parses once; `loaderDeps` makes invalidation explicit, not vibes.

</Notes>

# 2. Server functions are typed RPC

```ts
export const getStats = createServerFn({ method: "GET" })
  .validator((data): StatsSearch => validateStatsSearch(data))
  .handler(async ({ data }) => fetchPlausibleStats(data.period));
```

A server boundary you can call from loaders, hooks, and components.

# The part Next does not have

Server function middleware can run on the client and the server.

```ts
const middleware = createMiddleware({ type: "function" })
  .client(({ next }) => next({ sendContext: { clientRuntime } }))
  .server(({ context, next }) =>
    next({
      context: { requestId, clientRuntime: context.clientRuntime },
    }),
  );
```

Open `/slides/tanstack-start/showcase?feature=server`.

<Notes>

- THE take-home beat: one middleware with a `.client()` and a `.server()` half spanning the network.
- [DEMO] `showcase?feature=server` → press the button → request id changes, server-only context appears.
- [FALLBACK] SSR values are already on screen; point at `request id` + `server-only fn`.

</Notes>

# 3. RSC as an opt-in data primitive

```tsx
const Renderable = await renderServerComponent(
  <MDXContent
    source={post.raw}
    components={{ Sparkles, ChameleonHighlight }}
  />,
);

return { post, Renderable };
```

Server-render the heavy content. Compose client islands where they matter.

# This is not “RSC-first”

In Start, ordinary React components are interactive by default.

<Steps>

- Use RSC when it buys you something
- Cache it like route data
- Pass it through loader data
- Keep the client in charge of composition

</Steps>

# 4. Rendering is a dial

```tsx
createFileRoute("/blog/$slug")({
  /* full SSR */
});
createFileRoute("/dashboard")({ ssr: "data-only" });
createFileRoute("/playground")({ ssr: false });
```

Full SSR, data-only, or client-only — per route.

<Notes>

- Same route API, three settings: full SSR / data-only / client-only.
- 🗳 Second poll fires here ("which rendering knob?"). Let it run while you set up the hydration demo.

</Notes>

# 5. Hydration can wait

```tsx
<Hydrate when={visible({ rootMargin: "320px" })}>
  <BelowTheFoldChart />
</Hydrate>
```

The HTML is in the document. The JavaScript does not have to be.

Demo: `/slides/tanstack-start/showcase?feature=rendering`

<Notes>

- The conflation to break: rendering ≠ hydration. HTML now, JS later.
- [DEMO] `showcase?feature=rendering` → scroll to the island → view source shows markup; the counter hydrates on scroll.
- [FALLBACK] Just say the line and move on.

</Notes>

# The tradeoff

Next gives you a platform-shaped happy path.

Start gives you app-shaped primitives.

<Steps>

- More explicit
- More type-driven
- More portable
- More control over where React runs
